# uxdesign-guides

Solstice Design System

## Development

### Cloning

Clone the repository and change into the project directory:

```bash
git clone git@github.com:uw-it-aca/solstice-docs.git
cd solstice-docs
```

### Setup

Install dependencies and start the development server:

```bash
npm install
npm run dev
```

### Testing

Run the test suite with [Vitest](https://vitest.dev/):

```bash
# Run tests in watch mode
npm test

# Run tests once with a coverage report
npm run coverage
```

### Linting

Lint the codebase with [oxlint](https://oxc.rs/docs/guide/usage/linter):

```bash
# Report lint issues
npm run oxlint

# Automatically fix fixable lint issues
npm run oxlint:fix
```

### Formatting

Format the codebase with [oxfmt](https://oxc.rs/docs/guide/usage/formatter):

```bash
# Format files in place
npm run oxfmt

# Check formatting without writing changes
npm run oxfmt:check
```

## Deployment

Pushes to `main` trigger GitHub Actions, which build with Vite and deploy to `depts.washington.edu/ux/` via SCP.

### SSH Key Setup (one-time)

**Generate a deploy key on your local machine (no passphrase):**

```bash
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_deploy -N ""
```

**Copy the public key to the remote server:**

```bash
ssh-copy-id -i ~/.ssh/id_ed25519_deploy.pub ux@ovid.u.washington.edu
```

**Add to GitHub Secrets** (repo → Settings → Secrets and variables → Actions):

| Secret            | Value                                    |
| ----------------- | ---------------------------------------- |
| `SSH_HOST`        | `ovid.u.washington.edu`                  |
| `SSH_USER`        | `ux`                                     |
| `SSH_PRIVATE_KEY` | Output of `cat ~/.ssh/id_ed25519_deploy` |

**Verify locally:**

```bash
ssh -T ux@ovid.u.washington.edu
```

Should connect without a password prompt.

### Remote Server

- Web root: `~/public_html` → `/rc00/d87/ux/public_html`, a symlink to `/hw00/d87/ux`
  (`/rc00/d87/ux` is the account home and is not served)
- Site URL: https://depts.washington.edu/ux/
- Vanity URL: https://uxdesign.uw.edu/

### Vite Base Path

The `base` option in `vite.config.js` is set to `/ux/` to match the subpath on
the server, so asset URLs are baked as `/ux/assets/…` at build time. It is
applied to builds only (`command === "build"`); the dev server and
`vite preview` run at `/`, so `npm run dev` and `npm run preview` serve plain
URLs such as `http://localhost:5050/xd-team`. Preview strips the `/ux/` prefix
from asset requests and serves each route's pre-rendered page, the same way
the masked vanity host does on the server.

The same directory is served at **two mount points**:

| URL                              | Mount                              |
| -------------------------------- | ---------------------------------- |
| https://depts.washington.edu/ux/ | canonical, matches `base`          |
| https://uxdesign.uw.edu/         | UW URL masking, at the host's root |

On the masked vanity host there is no `/ux/` prefix, so two things bridge the
gap. The generated `.htaccess` strips the prefix when `HTTP_HOST` is a masked
host, which lets the baked-in asset URLs resolve; and `src/router/base.js`
resolves the router base against the current path, so generated links stay
clean on both (`/ux/xd-team` on depts, `/xd-team` on the vanity domain).

Masked hostnames are declared via the plugin's `maskedHosts` option in
`vite.config.js`.

### Status Codes

Pages are pre-rendered to static HTML during `npm run build` (`vite-ssg build`),
so crawlers, search engines and AI answer engines get each page's content
without running JavaScript. The home page is `dist/index.html`, the 404 page is
`dist/404.html`, and every other route is written to `dist/_html/<route>.html`.

Apache needs rules to serve those files at clean URLs. `dist/.htaccess` is
generated by `vite-plugin-htaccess.js` from the actual `vue-router` route table:

| Request                           | Response                          |
| --------------------------------- | --------------------------------- |
| `/ux/assets/…`, `/ux/images/…`    | the file itself                   |
| a known route, e.g. `/ux/xd-team` | `_html/xd-team.html` with **200** |
| anything else                     | `404.html` with a genuine **404** |

Unknown URLs are handled by `ErrorDocument 404 /ux/404.html`, so the 404 page
renders while the response carries a real 404 status. Adding a page under
`src/pages/` pre-renders it and updates the rules on the next build.

Each page's `<title>`, meta description, canonical URL and Open Graph tags
are rendered into its HTML as well. The layouts build them from the page's
`pageTitle` and the text of its `#lead` slot (see `src/utils/head.js`); pass the
layout a `description` prop to override the description, or `noindex` to keep
a page out of search indexes. Canonical URLs point to
`https://depts.washington.edu/ux/`, since the vanity host serves the same pages.

Indexable pages also carry schema.org structured data (JSON-LD): the
publishing organization, the site, the page as a `TechArticle` with its
breadcrumb trail, and a `dateModified`. That date is the page's `lastReviewed`
(`YYYY-MM-DD` in its `data()`) when set, so authors can mark changes that matter
to readers; otherwise it is the author date of the page file's last git commit. Dates need full git history, so they are left out of builds from a
shallow clone. The same date is shown at the bottom of each page as
"Last updated", followed by the `author` from the page's `data()` if it has one.

The build also writes `sitemap.xml` (every pre-rendered page, as a canonical
`https://depts.washington.edu/ux/…` URL) and `robots.txt` (all crawlers
allowed, pointing to the sitemap). Crawlers only read `robots.txt` at a host's
root, so it takes effect on `uxdesign.uw.edu` but not under
`depts.washington.edu/ux/`; submit the sitemap URL in Google Search Console and
Bing Webmaster Tools so it is found for the canonical host.

Pages that still contain placeholder text are tracked in
[`docs/placeholder-content.md`](docs/placeholder-content.md).

Code that uses `window` or `document` has to run in `mounted()` (or be imported
dynamically there). At module level or in `created()` it breaks the build,
because pages are rendered in Node, where those globals don't exist.

Legacy files from the previous static site still live in the web root and are
served as-is by the file/directory passthrough rule, since SCP merges rather
than replaces. Check for collisions before adding a page whose route matches an
existing file or directory name.

Verify after a deploy:

```bash
# canonical host
curl -sI https://depts.washington.edu/ux/xd-team | head -1   # expect 200
curl -sI https://depts.washington.edu/ux/nope    | head -1   # expect 404

# masked vanity host
curl -sI https://uxdesign.uw.edu/xd-team | head -1           # expect 200
curl -sI https://uxdesign.uw.edu/nope    | head -1           # expect 404
```

This relies on `AllowOverride` permitting `mod_rewrite` and `ErrorDocument` in
`.htaccess` on the server. The rules avoid `<If>` blocks, which would also
require `AllowOverride All`.
